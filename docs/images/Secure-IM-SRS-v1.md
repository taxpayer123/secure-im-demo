# 安全即时通讯软件需求规格说明书 (SRS)

## 1. 引言

### 1.1 编写目的
本文档旨在明确“基于 OpenIM 的安全即时通讯软件”（以下简称“本项目”）的功能需求、安全需求及非功能需求。本文档将作为团队内部开发、AI 辅助编码以及期末课程设计答辩的核心基准文件。

### 1.2 项目背景
本项目属于信息安全课程设计。随着信息泄露事件频发，用户对通信隐私的关注度日益提升。本项目基于开源的 **OpenIM Electron Demo** 进行二次开发，旨在剥离复杂的底层音视频及网络通信逻辑，将核心精力集中于**应用层加密**与**客户端安全加固**，打造一款具备高隐私保护特性的轻量级即时通讯工具。

---

## 2. 总体描述

### 2.1 产品愿景
开发一款轻量级的安全聊天桌面应用，核心主打“隐私与防泄漏”。在具备基础文本通信能力的前提下，实现类似 Telegram 的核心安全特性（如端到端加密、本地防窥探等），验证现代密码学在工程实践中的应用。

### 2.2 运行环境与技术栈
* **宿主环境:** Windows 10/11, macOS
* **前端框架:** Electron + React/Vue (继承自 OpenIM Demo)
* **核心安全库:** `WebCrypto` (加解密算法), `better-sqlite3-multiple-ciphers` (数据库加密)
* **通信底层:** OpenIM SDK

---

## 3. 核心功能需求 (Functional Requirements)

为了适应团队开发节奏，项目采用“核心加固，外围简化”策略。以下为必须实现的功能模块：

### 3.1 FR-01: 安全登录与身份校验
**描述:** 防止非法用户通过暴力破解获取账号访问权限。
* **常规登录:** 用户通过账号密码进行登录。
* **安全加固 (图形验证码):** 连续登录失败 3 次后，强制要求输入复杂图形验证码或进行滑块验证。
* **多端登录提示:** (可选) 当同一账号在不同设备登录时，界面需弹出安全警告。

### 3.2 FR-02: 基础聊天能力 (依赖 OpenIM)
**描述:** 实现可靠的消息收发。
* **单聊:** 支持用户间的文本消息实时发送与接收。
* **状态同步:** 保证消息的送达状态（已送达/已读）准确显示。

### 3.3 FR-03: 敏感词审查机制 (合规性演示)
**描述:** 满足信息安全审计的基本要求。
* **前端过滤:** 在调用发送接口前，对文本内容进行本地敏感词词库匹配。
* **拦截提示:** 若包含如“暴力”、“违禁”等测试敏感词，拒绝发送并在界面提示“消息包含不合规内容，已被本地安全策略拦截”。

## 4. 核心安全需求 (Security Requirements)

这是本课程设计的**核心得分点**，重点展示信息安全技术的落地。

### 4.1 SR-01: 端到端加密 (E2EE)
**描述:** 确保消息在传输过程中以及在服务器端均以密文形态存在。
* **加密算法:** 采用 **AES-256-GCM** 对称加密算法。
* **密钥管理:** 演示阶段采用预共享密钥或极简的 Diffie-Hellman 密钥交换协议生成会话密钥。
* **业务逻辑:**
    * 发送端：在拦截 OpenIM 发送动作，提取明文，使用 AES 加密后，将密文载荷传给 OpenIM SDK。
    * 接收端：OpenIM SDK 收到密文后，界面渲染前进行 AES 解密，若解密失败则显示“解密失败的乱码”。

### 4.2 SR-02: 本地存储加密
**描述:** 防止攻击者通过物理接触获取计算机内的聊天记录文件。
* **数据库加密:** 替换 Electron 原生的 SQLite 存储方案，集成 **SQLCipher**。
* **密钥派生:** 用户的本地数据库解密密钥不应硬编码，需通过用户的登录密码经过 PBKDF2 或 Argon2 算法派生得出。

### 4.3 SR-03: 隐私保护机制 (防截屏与阅后即焚)
**描述:** 防止通信内容被终端用户恶意留存。
* **防截屏 (Windows/macOS):** 调用 Electron 主进程 API (`setContentProtection(true)`)，当第三方软件尝试录屏或截屏时，应用窗口呈现全黑。
* **阅后即焚 (UI 级销毁):** 用户可开启“闪照/闪聊”模式，接收方查看消息 10 秒后，触发前端回调，将消息从本地数据库中硬删除（Physical Delete）并从 DOM 树中移除。

### 4.4 SR-04: 多因子认证 (MFA - TOTP) 【备选/进阶】
**描述:** 在密码登录的基础上，增加基于时间的一次性密码校验，防范密码泄露风险。
* **技术实现:** 集成 `otplib` 生成与校验 TOTP 动态码，使用 `qrcode` 在客户端生成绑定二维码。
* **业务逻辑:**
    * 首次配置：应用生成密钥（Secret），展示二维码，用户使用 Google Authenticator 或 Microsoft Authenticator 扫码绑定。密钥存入本地加密数据库。
    * 登录校验：输入密码后，弹出二次验证框，要求输入手机上的 6 位动态码，校验通过后才允许放行进入主界面。

### 4.5 SR-05: 现代无密码认证 (Passkey/WebAuthn) 【备选/挑战】
**描述:** 拥抱 FIDO2 标准，利用设备硬件（指纹、面容识别、Windows Hello）代替传统密码进行安全登录。
* **技术实现:** 在 Electron 中调用 WebAuthn API（通过 `@simplewebauthn/browser` 或原生 API）。
* **业务逻辑:**
    * 注册阶段：调用系统底层的生物识别授权，生成公私钥对。私钥安全存储于系统安全硬件（TPM/Secure Enclave）中，公钥和凭据 ID 存入本地数据库。
    * 登录阶段：触发鉴权挑战，用户验证指纹/面部后，应用使用私钥对挑战进行签名并验证，实现无缝且极高安全性的登录。

## 5. 需求矩阵与实施优先级

为确保团队在有限的时间和技术水平内顺利交付，特制定以下优先级矩阵。

| 需求编号 | 需求名称 | 实现难度 | 优先级 | 备注 / AI 辅助建议 |
| :--- | :--- | :--- | :--- | :--- |
| **SR-01** | 端到端加密 (AES) | 中 | **高 (必做)** | 答辩核心。直接让 AI 写一个 `crypto.js` 工具类进行文本拦截。 |
| **FR-01** | 安全登录 (验证码) | 低 | **高 (必做)** | 找开源 React/Vue 验证码组件，AI 辅助接入。 |
| **SR-03** | 防截屏 API 调用 | 低 | 中 (加分项) | 仅需在 Electron `main.js` 添加一行代码即可。 |
| **SR-04** | 多因子认证 MFA | 中 | 中 (挑战项) | MFA (TOTP) 代码量少、视觉效果好（能掏出手机扫码） |
| **SR-05** | 现代无密码认证 (Passkey/WebAuthn) | 中 | 中 (挑战项) | 紧跟“无密码（Passwordless）”和现代身份鉴权的前沿安全趋势 |
| **SR-02** | 本地数据库加密 | 高 | 低 (挑战项) | 涉及原生模块编译 (node-gyp)，容易报错，视时间定。 |

---

## 6. 附录：非技术协作规范

* **UI 视觉:** 尽量保持 OpenIM Demo 原有布局，仅在右上角增加“安全锁”图标或“当前会话已加密”的绿色盾牌提示，增强答辩时的视觉表现力。
